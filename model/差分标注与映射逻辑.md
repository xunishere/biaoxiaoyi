# 差分标注与映射逻辑

## 0. 前置：从评分页到 score_unit

差分标注的输入是 `procurement_score_units_draft.json`（或经 MiMo 规整后的 `procurement_score_units_mimo_refined.json`）。这一节描述这份草稿怎么从原始采购 PDF 一路生成出来。本阶段不做评分判断，也不做主客观判断，只保留原文。

### 0.1 评分页定位

用 `pdftotext` 抽出 PDF 每一页的纯文本，再按关键词组合打分：

| 信号类型 | 关键词组合 |
|---|---|
| 起始页信号 | `综合评分法` + `评分规则` + 三列表头同现（`评分项目`/`分值区间`/`评分办法`）+ 分值区间 `0~10` 多次出现 |
| 续接页信号 | 分值区间多次出现 + `一、评审内容/二、评审标准` + `小项`/`不得分` |

最高得分页判为起始页，之后逐页判断续接，直到出现非评分相关章节标题。

输出 `procurement_scoring_page_range.json`。

### 0.2 评分页渲染

用 `pdftoppm` 按 180 DPI 把评分页渲染为 PNG，保存到 `pp_structurev3_input/procurement_scoring_pages/`。

### 0.3 PP-StructureV3 OCR + 表格识别

加载 PP-StructureV3（GPU 推理），启用：

```text
use_table_recognition=True
use_seal_recognition=False
use_formula_recognition=False
use_chart_recognition=False
use_region_detection=True
```

对每一页输出 `page-{N}_res.json`，关键字段：

| 字段 | 用途 |
|---|---|
| `parsing_res_list[*].block_label` | `table_title` / `table` / `figure_title` 等版面区域 |
| `table_res_list[*].cell_box_list` | 单元格几何位置（行列归并的客观依据） |
| `table_res_list[*].pred_html` | 模型给的 HTML 表格结构（仅参考，行错位时不用） |
| `table_res_list[*].table_ocr_pred.rec_texts + rec_boxes` | 每个 OCR 行的文本和 bbox |

### 0.4 OCR 行 → 评分单元

不依赖 PP-StructureV3 给的 HTML 行号（长单元格场景下容易行错位），而是基于 OCR 行的几何位置自切：

1. 用表头三列文字（`评分项目` / `分值区间` / `评分办法`）的中心点推 `left_mid`、`right_mid` 两条列边界。
2. 同一页内 OCR 行按 y 坐标聚类成行。
3. 每行内的 OCR 文本按 cx 落到 `item` / `range` / `method` 三列。
4. 状态机判定：当 `item` 列出现非表头、非 `N~M` 的 2~40 字短词，且 `range` 列出现 `0~10` 这类范围 → 开新评分单元，后续行追加到当前单元，直到下一个评分单元出现。
5. 跨页天然支持：多页按顺序遍历同一个 `units` 状态。

输出 `procurement_score_units_draft.json`，每条 `score_unit` 含：

```json
{
  "unit_id": "TU-DRAFT-002",
  "unit_name": "需求理解",
  "score_range_text": "0~12",
  "page_start": 27,
  "page_end": 28,
  "raw_text": "采购评分单元原文（OCR）",
  "source_line_ids": ["p27-t1-l3", "p27-t1-l4", "..."],
  "warnings": []
}
```

### 0.5 MiMo OCR 文本规整（可选）

如果 `.env` 配置了 MiMo（`MIMO_API_KEY` + `MIMO_BASE_URL`），对每条 `score_unit` 调一次 MiMo 做机械整理：

MiMo 允许做的：

```text
修复 OCR 断行
修复中文词中间空格
修复跨行断词
统一标点
在“一、评审内容”“二、评分标准”等处补段落换行
删除疑似噪声字符（如孤立的“广”“c”），但必须写入 uncertain_points
```

MiMo 不允许做的：

```text
解释评分规则
新增采购文件没有的信息
改写含义
判断主观/客观
打分
```

输出 `procurement_score_units_mimo_refined.json`，是 §2 评分细则数据集的直接输入源。

### 0.6 阶段产出

| 文件 | 来源 | 用途 |
|---|---|---|
| `procurement_scoring_page_range.json` | §0.1 | 评分页范围定位 |
| `pp_structurev3_input/procurement_scoring_pages/page-*.png` | §0.2 | PP-StructureV3 输入 |
| `pp_structurev3_output/procurement_scoring_pages_with_table/page-*_res.json` | §0.3 | OCR + 表格识别结果 |
| `procurement_score_units_draft.json` | §0.4 | 评分单元草稿 |
| `procurement_score_units_mimo_refined.json` | §0.5（可选） | MiMo 规整后的评分单元（§2 输入） |

§2 的 `procurement_scoring_criteria.json` 在 §0.5（若启用）或 §0.4 的输出基础上拆分得到。

## 1. 当前目标

当前阶段维护的是三类数据：

| 数据集 | 文件 | 含义 |
|---|---|---|
| 采购评分细则数据集 | `dataset_extraction_output/procurement_scoring_criteria.json` | 从采购文件评分表中拆出的评分细则 |
| 投标响应片段数据集 | `dataset_extraction_output/bid_response_fragments.json` | 从投标技术文件中拆出的可关联响应片段 |
| 采购-投标映射数据集 | `dataset_extraction_output/procurement_bid_mapping.json` | 每条采购评分细则对应 0 个或多个投标响应片段 |

这里的“差分标注”不是比较两份文本的字面差异，也不是打分，而是维护一张关系表：

```text
采购评分细则 -> 投标响应片段列表
```

每条采购评分细则可以对应：

```text
0 个投标片段
1 个投标片段
多个投标片段
```

第一版只判断是否有关联，不做：

```text
部分响应
缺失项分析
得分预测
文本质量评价
投标文件优化建议
```

## 2. 采购评分细则数据

采购侧的基本单位不是评分大项，也不是整个评分单元，而是评分细则。

例如“需求理解 0~12”会拆成 4 条细则：

| 评分单元 | 评分细则 | 分值 |
|---|---|---|
| 需求理解 | 应用环境、体系结构需求和实施要求等需求内容的理解程度 | 3分 |
| 需求理解 | 系统功能需求、性能要求理解程度 | 3分 |
| 需求理解 | 合理化建议、风险分析及控制方案 | 3分 |
| 需求理解 | 重点、难点问题的分析与措施 | 3分 |

每条评分细则保留以下字段：

```json
{
  "criterion_id": "PC-002-01",
  "score_unit_id": "TU-DRAFT-002",
  "score_unit_name": "需求理解",
  "criterion_name": "应用环境、体系结构需求和实施要求等需求内容的理解程度",
  "object": "应用环境、体系结构需求和实施要求等需求内容",
  "feature": "理解程度",
  "evaluation_method": "该细则最高3分，按采购文件评分标准判断",
  "score_text": "3分",
  "scoring_type": "subjective",
  "raw_text": "采购文件中的评分细则原文"
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `criterion_id` | 评分细则ID |
| `score_unit_id` | 所属评分单元ID |
| `score_unit_name` | 所属评分单元名称 |
| `criterion_name` | 评分细则名称 |
| `object` | 细则评价对象 |
| `feature` | 细则关注特性 |
| `evaluation_method` | 给分或判断方式的原文规整 |
| `score_text` | 该细则对应分值 |
| `scoring_type` | `subjective` 或 `objective` |
| `raw_text` | 采购文件原文依据 |

采购细则拆分逻辑：

1. 优先按 `1、...（3分）`、`2、...（4分）` 这类明确分值小项拆分。
2. 如果评分单元没有明确小项分值，则保留为一条整体细则。
3. `报价得分`、`类似项目的经验` 等客观项也进入细则数据集。
4. MiMo 只允许补全结构字段，不允许新增采购文件中不存在的评分要求。

## 3. 投标响应片段数据

投标侧的基本单位是“响应片段”，不是原始章节。

当前只处理投标文件中“技术响应文件”之后的内容。

响应片段由投标文件标题层级和内容组成：

```json
{
  "fragment_id": "BF-0004",
  "source_section_ids": ["BID-SEC-0004"],
  "heading_path": [
    "需求理解",
    "应用环境、体系结构需求与实施要求的理解",
    "应用环境需求的深度理解"
  ],
  "top_score_direction": "需求理解",
  "text": "投标正文原文",
  "table_text": "",
  "image_refs": [],
  "char_count": 2218,
  "paragraph_count": 20,
  "table_count": 0,
  "image_count": 0
}
```

投标片段整理规则：

1. 空标题不作为独立响应片段。
2. 空标题仍保留在 `heading_path` 中，作为定位上下文。
3. 片段必须至少包含正文、表格文本、图片引用三者之一。
4. 表格统一转成 `table_text`。
5. 图片暂不做图像理解，只保留 `image_refs` 和数量。
6. `top_score_direction` 取标题路径中的一级方向，例如 `需求理解`、`实施方案`、`培训方案`。

## 4. 映射数据

映射数据维护的是：

```text
一条采购评分细则 -> 0 个或多个投标响应片段
```

结构示例：

```json
{
  "criterion_id": "PC-002-01",
  "score_unit_id": "TU-DRAFT-002",
  "score_unit_name": "需求理解",
  "criterion_name": "应用环境、体系结构需求和实施要求等需求内容的理解程度",
  "linked_bid_fragments": [
    {
      "fragment_id": "BF-0002",
      "heading_path": [
        "需求理解",
        "应用环境、体系结构需求与实施要求的理解",
        "应用环境需求的深度理解"
      ],
      "evidence_text": "投标文件中的命中原文",
      "match_reason": "标题和正文响应该采购评分细则",
      "decision_source": "mimo-v2.5-pro"
    }
  ],
  "candidate_fragment_ids": ["BF-0002", "BF-0003"]
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `criterion_id` | 当前采购评分细则 |
| `linked_bid_fragments` | 最终认为有关联的投标响应片段 |
| `fragment_id` | 投标响应片段ID |
| `evidence_text` | 命中证据文本 |
| `match_reason` | 命中原因 |
| `decision_source` | 命中来源，如 `mimo-v2.5-pro` 或 `structural_rule` |
| `candidate_fragment_ids` | 进入候选召回的片段ID |

`linked_bid_fragments` 可以为空数组。例如：

```json
{
  "criterion_id": "PC-001-01",
  "score_unit_name": "报价得分",
  "criterion_name": "报价得分",
  "linked_bid_fragments": []
}
```

这是允许的，因为当前投标片段范围只取技术响应文件，报价得分不一定有技术响应片段。

## 5. 当前映射生成逻辑

当前映射分三步：

```text
采购评分细则
-> 候选投标片段召回
-> MiMo 命中判断
-> 结构规则兜底
-> 输出最终 linked_bid_fragments
```

### 5.1 候选召回

候选召回只用于缩小模型判断范围。

召回依据：

1. 投标片段标题路径是否包含评分单元名。
2. 投标片段标题路径是否包含评分细则关键词。
3. 投标片段正文是否包含评分细则关键词。

每条采购细则最多召回 10 个候选片段。

候选片段不等于最终命中片段。

### 5.2 MiMo 命中判断

MiMo 的任务只限于判断候选投标片段是否响应该采购评分细则。

MiMo 不允许：

```text
打分
评价文本好坏
新增候选之外的片段
补充采购文件没有的要求
生成投标优化建议
```

MiMo 输出：

```json
{
  "linked_bid_fragments": [
    {
      "fragment_id": "BF-0002",
      "evidence_text": "来自候选片段的原文证据",
      "match_reason": "为什么认为该片段响应该细则"
    }
  ]
}
```

如果没有命中，则输出：

```json
{
  "linked_bid_fragments": []
}
```

### 5.3 结构规则兜底

由于模型有时会过于保守，当前增加了结构规则兜底。

当满足以下条件时，可以直接认为存在结构关联：

```text
投标片段 top_score_direction 与采购评分单元一致
且投标片段 heading_path 命中评分细则核心词
```

例如：

```text
采购细则：生活垃圾分类智慧收运系统-智慧收运移动端
投标片段标题：软件模块开发方案及软件功能内容 / 生活垃圾分类智慧收运系统-智慧收运移动端开发方案及功能内容
```

这类标题路径已经明确对应评分细则，即使模型漏判，也会保留为映射关系。

结构规则只做关系维护，不代表该片段能得高分。

## 7. 后续人工复核口径

人工复核时重点看两类问题：

| 问题 | 含义 |
|---|---|
| 漏标 | 采购细则明明有投标响应，但映射中没有挂上 |
| 误标 | 投标片段只是关键词相似，但并没有响应该评分细则 |

后续可以基于 `procurement_bid_mapping.json` 增加人工审核字段：

```json
{
  "accepted": true,
  "review_comment": "",
  "manual_added_fragment_ids": [],
  "manual_removed_fragment_ids": []
}
```

但当前阶段暂不写人工审核字段，先保持自动映射结果干净。

## 8. 下一步：响应文本特征抽取

映射完成后，下一步不是直接生成投标文件，也不是预测分数，而是从已命中的投标片段中抽取“可学习的文本结构”。

新增输出：

| 数据集 | 文件 | 含义 |
|---|---|---|
| 评分细则响应文本特征数据集 | `dataset_extraction_output/criterion_response_features.json` | 每条采购评分细则对应的客观证据特征或主观写作结构特征 |
| 评分细则响应文本特征说明 | `dataset_extraction_output/criterion_response_features.md` | 便于人工查看的 Markdown 版本 |

这一阶段的输入只来自三份正式数据：

```text
procurement_scoring_criteria.json
bid_response_fragments.json
procurement_bid_mapping.json
```

不重新解释采购文件，不修改采购评分细则，也不新增评分要求。

### 8.1 客观评分项

客观项的目标是抽“证据核验结构”，不是学习写法。

例如：

| 客观类型 | 关注结构 |
|---|---|
| 报价公式型 | 投标报价、评标基准价、价格分公式 |
| 合同案例型 | 合同名称、签订日期、服务期限、盖章页、合同扫描件 |
| 人员数量型 | 人员数量、岗位角色、人员清单 |
| 人员资质型 | 人员姓名、岗位角色、证书名称、证书等级、社保证明 |

客观项输出到 `objective_evidence_features`：

```json
{
  "evidence_type": "price_formula",
  "verification_mode": "公式计算型",
  "required_evidence_terms_from_criterion": ["报价", "公式", "评标基准价"],
  "candidate_evidence_fields": ["投标报价", "评标基准价", "价格分公式"],
  "detected_evidence_terms_in_linked_fragments": [],
  "note": "本结构只描述客观项的证据核验字段，不做得分计算。"
}
```

### 8.2 主观评分项

主观项的目标是抽“投标响应怎么组织文本”，也就是后续学习写作思路的基础。

主观项输出到 `subjective_writing_features`，包含：

| 字段 | 含义 |
|---|---|
| `heading_patterns` | 命中片段的标题路径、层级深度、叶子标题 |
| `coverage_terms_found` | 投标片段中命中的评分细则关键词 |
| `project_specific_terms` | 投标片段中的项目化词语，如闵行区、智慧收运、街镇等 |
| `content_modules` | 片段中出现的内容模块，如需求理解、架构设计、实施计划、风险控制等 |
| `writing_structure` | 片段的展开顺序，如先总述、再分层拆解、再补执行路径 |
| `execution_elements` | 步骤、流程、计划、分工、交付、测试、验收等执行要素 |
| `format_elements` | 是否使用表格、图片、编号条目、标题层级 |

主观项示例：

```json
{
  "criterion_id": "PC-002-01",
  "scoring_type": "subjective",
  "linked_fragment_ids": ["BF-0002", "BF-0003", "BF-0004"],
  "subjective_writing_features": {
    "rule_features": {
      "content_modules": ["采购需求理解", "系统架构或分层设计", "实施步骤与计划"],
      "writing_structure": ["先给出项目定位或需求理解结论", "再按架构、模块或业务对象拆解展开"],
      "project_specific_terms": ["闵行区", "生活垃圾", "智慧收运"],
      "execution_elements": ["步骤流程", "阶段计划", "风险控制"]
    },
    "model_features": null
  }
}
```

### 8.3 MiMo 在这一阶段的作用

MiMo 在这一阶段只允许做“结构抽取”：

```text
从已命中片段中归纳内容模块
从已命中片段中归纳展开顺序
从已命中片段中摘出项目化表达
从已命中片段中识别执行要素和表达载体
```

MiMo 不允许：

```text
打分
评价写得好不好
生成新的投标文本
新增采购文件没有的要求
把投标文本特征反写成采购评分细则
```

当前已先落地规则版特征抽取；如果开启 MiMo，可在规则特征基础上补充 `model_features`。
