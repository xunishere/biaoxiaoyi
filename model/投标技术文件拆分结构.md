# 投标技术文件拆分结构

## 一、目标

本文档定义投标技术文件的数据拆分结构。

投标技术文件不是简单按页切分，也不是只提取全文摘要，而是要围绕采购文件的评分细则建立可关联的响应数据。

核心结构为：

```text
标题索引 -> 响应单元 -> 文本/图表内容 -> 内容特征
```

其中，标题索引用于定位投标文件中的章节层级；响应单元用于对应采购文件中的评分细则；文本和图表是投标文件实际用于响应评分细则的内容。

## 二、数据结构

```json
{
  "bid_technical_file": {
    "project_name": "项目名称",
    "bidder_name": "投标单位",
    "source_file": "投标文件名称",
    "title_index": [
      {
        "title_id": "BT-001",
        "title_name": "一级标题",
        "title_level": 1,
        "parent_title_id": null,
        "title_order": 1,
        "page_start": 43,
        "page_end": 87,
        "related_score_detail_ids": ["TD-001-01-01"],
        "children": []
      }
    ],
    "response_units": [
      {
        "response_id": "BR-001",
        "related_score_detail_id": "TD-001-01-01",
        "related_score_unit_id": "TU-001-01",
        "related_subject_id": "TS-001",
        "title_path": [
          "1. 需求理解",
          "1.2 应用环境、体系结构需求与实施要求的理解",
          "1.2.2 体系结构需求的深度理解"
        ],
        "content_blocks": [
          {
            "block_id": "BB-001",
            "block_type": "text",
            "content": "文本内容",
            "content_features": {}
          },
          {
            "block_id": "BB-002",
            "block_type": "table",
            "content": "表格内容或表格结构",
            "content_features": {}
          },
          {
            "block_id": "BB-003",
            "block_type": "figure",
            "content": "图示说明或图片引用",
            "content_features": {}
          }
        ]
      }
    ]
  }
}
```

## 三、标题索引 title_index

标题索引用于保存投标文件的一、二、三、四级标题结构。

它的作用是：

1. 定位投标文件内容；
2. 保留章节层级；
3. 记录每个章节可能对应的采购评分细则；
4. 为后续检索、关联和回溯原文提供索引。

字段结构：

| 字段 | 含义 |
|------|------|
| title_id | 标题ID |
| title_name | 标题名称 |
| title_level | 标题层级，如1、2、3、4 |
| parent_title_id | 父标题ID |
| title_order | 标题顺序 |
| page_start | 起始页 |
| page_end | 结束页 |
| related_score_detail_ids | 该标题可能响应的采购评分细则ID |
| children | 子标题 |

示例：

| 标题层级 | 标题 | 对应采购评分细则 |
|----------|------|------------------|
| 一级 | 1. 需求理解 | 需求理解相关细则 |
| 二级 | 1.2 应用环境、体系结构需求与实施要求的理解 | 应用环境、体系结构、实施要求理解 |
| 三级 | 1.2.2 体系结构需求的深度理解 | 体系结构需求相关细则 |
| 四级 | 1.2.2.1 数据资源层设计理解 | 体系结构中的数据层要求 |

## 四、响应单元 response_unit

响应单元是投标文件中用于响应某条采购评分细则的内容集合。

一个响应单元可以来自一个章节，也可以来自多个标题下的文本、表格和图示。

字段结构：

| 字段 | 含义 |
|------|------|
| response_id | 响应单元ID |
| related_score_detail_id | 对应采购文件评分细则ID |
| related_score_unit_id | 对应采购文件评分单元ID |
| related_subject_id | 对应采购文件科目ID |
| title_path | 投标文件中的标题路径 |
| content_blocks | 该响应单元下的文本块、表格块、图示块 |

后续做关联时，基本关系是：

```text
采购评分细则 -> 投标标题索引 -> 投标响应单元 -> 文本/图表内容
```

## 五、内容块 content_block

投标响应内容可拆为不同类型的内容块。

| block_type | 含义 |
|------------|------|
| text | 普通文本段落 |
| table | 表格 |
| figure | 图片、架构图、流程图、甘特图等 |
| list | 列表 |
| evidence | 证书、合同、截图等证明材料 |

每个内容块都需要保存：

| 字段 | 含义 |
|------|------|
| block_id | 内容块ID |
| block_type | 内容块类型 |
| content | 内容文本、表格结构或图片说明 |
| page_start | 内容起始页 |
| page_end | 内容结束页 |
| title_id | 所属标题ID |
| content_features | 内容特征 |

## 六、文本内容结构

文本不是只保存字符串，还要保存与评分相关的文本特征。

文本块结构：

```json
{
  "block_id": "BB-001",
  "block_type": "text",
  "title_id": "BT-001",
  "content": "投标文件正文内容",
  "content_features": {
    "word_count": 850,
    "is_on_topic": true,
    "topic_keywords": ["智慧收运", "一网统管", "体系结构"],
    "coverage_points": ["应用环境", "体系结构", "实施要求"],
    "has_project_specific_content": true,
    "has_steps_or_measures": true,
    "has_quantitative_description": false,
    "has_risk_analysis": false
  }
}
```

文本特征：

| 特征 | 含义 |
|------|------|
| word_count | 字数 |
| is_on_topic | 是否切题 |
| topic_keywords | 与评分细则相关的关键词 |
| coverage_points | 覆盖了哪些评分检查点 |
| has_project_specific_content | 是否结合本项目背景、需求或业务场景 |
| has_steps_or_measures | 是否有步骤、流程、措施 |
| has_quantitative_description | 是否有数量、时间、频率、指标等量化描述 |
| has_risk_analysis | 是否包含风险分析 |

文本内容后续可用于判断：

```text
是否写了
写了多少
是否切题
是否覆盖评分细则
是否只是泛泛描述
是否有具体措施
```

## 七、图表内容结构

图表包括架构图、流程图、路线图、甘特图、组织架构图、人员表、功能表、响应表等。

图表块结构：

```json
{
  "block_id": "BB-002",
  "block_type": "figure",
  "title_id": "BT-001",
  "caption": "系统总体架构图",
  "content": "图示说明或OCR提取内容",
  "content_features": {
    "figure_type": "architecture_diagram",
    "has_caption": true,
    "is_related_to_score_detail": true,
    "related_objects": ["系统架构", "数据资源层", "核心应用层"],
    "visual_quality": "unknown",
    "has_clear_hierarchy": true,
    "has_labels": true,
    "has_quantity_or_scale": false,
    "supports_text_content": true
  }
}
```

图表特征：

| 特征 | 含义 |
|------|------|
| figure_type | 图表类型，如架构图、流程图、甘特图、表格 |
| has_caption | 是否有标题或说明 |
| is_related_to_score_detail | 是否与评分细则相关 |
| related_objects | 图表涉及的对象，如架构、流程、人员、计划 |
| visual_quality | 图表质量，可先保留unknown，后续模型判断 |
| has_clear_hierarchy | 是否层次清晰 |
| has_labels | 是否有清楚标注 |
| has_quantity_or_scale | 是否包含数量、时间、比例等信息 |
| supports_text_content | 是否支撑周边文字说明 |

图表后续可用于判断：

```text
图表数量是否充足
图表是否与评分细则相关
图表是否支撑文本说明
图表是否清晰、美观、有层次
图表是否包含必要对象或流程
```

当前阶段只提取图表结构和基础特征，不在拆分阶段直接判断“美观”得分。

## 八、文本与图表的关系

投标文件中，文本和图表通常不是孤立存在的。

例如：

```text
系统架构设计章节
-> 一段文字说明总体架构
-> 一个系统架构图
-> 一个模块说明表
```

因此，响应单元中需要保留文本和图表的组合关系。

建议保存：

| 字段 | 含义 |
|------|------|
| block_order | 内容块顺序 |
| nearby_text_block_ids | 图表附近的文字说明 |
| referenced_figure_ids | 文本引用的图表 |
| supports_score_detail | 是否支撑对应评分细则 |

## 九、与采购评分细则的关系

投标技术文件拆分不是孤立拆分，而是为了响应采购文件评分细则。

对应关系：

```text
采购文件：
科目 -> 评分单元 -> 评分细则

投标文件：
标题索引 -> 响应单元 -> 文本/图表内容

关联关系：
评分细则 -> 响应单元
```

也就是说，每个投标响应单元都应尽量标注它对应的采购评分细则。

示例：

| 采购评分细则 | 投标标题路径 | 响应内容 |
|--------------|--------------|----------|
| 系统架构合理 | 3. 系统建设总体服务方案 / 3.3 系统总体架构设计 | 架构说明文本 + 系统架构图 |
| 实施计划科学合理 | 4. 实施方案 / 4.3 实施工作计划、工作流程与时间安排 | 实施阶段说明 + 计划表 |
| 培训方案完整详尽 | 9. 培训方案 / 9.2 培训整体规划与总体实施计划 | 培训计划文本 + 培训安排表 |
| 团队人数不少于20人 | 7. 项目服务团队配备情况 / 7.2 拟委派人员情况表 | 人员表 |

## 十、提取规则

1. 先提取投标技术文件的一、二、三、四级标题，建立标题索引。
2. 根据采购文件评分细则，将标题或章节初步关联到对应评分细则。
3. 在每个标题下继续拆分文本块、表格块、图表块和证明材料块。
4. 对文本块提取字数、关键词、覆盖检查点、是否切题、是否有措施等基础特征。
5. 对图表块提取图表类型、标题、说明、关联对象、是否有层次、是否有标注等基础特征。
6. 保留文本与图表的前后关系，避免把图表和说明文字割裂。
7. 当前阶段只做结构化拆分和基础特征提取，不直接替模型判断最终分数。

## 十一、说明

投标技术文件的拆分粒度应服务于评分细则。

如果只按页切分，会丢失章节逻辑；如果只按标题切分，又会丢失图表、表格和段落的细节。因此应采用：

```text
标题索引 + 响应单元 + 内容块
```

的方式。

其中：

| 对象 | 用途 |
|------|------|
| 标题索引 | 定位章节层级 |
| 响应单元 | 对齐采购评分细则 |
| 文本块 | 保存具体方案描述 |
| 图表块 | 保存架构图、流程图、计划表等支撑内容 |
| 内容特征 | 为后续模型判断响应质量提供输入 |

这样拆出来的数据，才能用于后续判断：

```text
投标文件是否响应了采购评分细则；
响应内容是否充分；
文本和图表是否共同支撑该评分细则；
客观材料是否满足采购条件；
主观方案是否具备足够内容基础。
```
