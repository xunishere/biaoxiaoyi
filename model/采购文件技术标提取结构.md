# 采购文件技术标提取结构

## 一、目标

本文档定义从采购文件中提取“技术标评分标准”的数据结构。

技术标提取的核心不是整篇采购文件，而是综合评分法中与技术方案、实施方案、服务能力、团队配置、验收培训等相关的评分内容。

需要抽取的主干结构是：

```text
科目 -> 评分单元 -> 评分细则 -> 细则对象 / 细则特性 / 评价方法
```

其中，每一条评分细则都必须标注为：

```text
主观评分 / 客观评分
```

因为主观评分和客观评分后续的打分过程不同。

## 二、数据结构

```json

    "subjects": [

        "subject_name": "科目名称",
        "score_range": {
          "min": 0,

          {
            "unit_id": "TU-001-01",
            "unit_name": "评分单元名称",
            "score_range": {
              "min": 0,
              "max": 3
            },
            "score_details": [
              {
                "detail_id": "TD-001-01-01",
                "detail_name": "评分细则名称",

                "scoring_feature": "评价特性",
                "evaluation_method": {
                  "method_type": "level_judgement",
                  "levels": [
                    {
                      "score_range": {
                        "min": 3,

                    },

                        "min": 1,

                      },
                      "condition_text": "采购文件中的原文评分条件"
                    },
                    {
```

## 三、字段解释

### 1. 科目 subject

科目是技术标评分中的大项。

例如：

| 科目 | 分值区间 |
|------|----------|
| 需求理解 | 0~12 |
| 系统建设总体服务方案 | 0~15 |
| 实施方案 | 0~12 |
| 软件模块开发方案及软件功能内容 | 0~18 |
| 服务综合支撑能力 | 0~8 |
| 项目服务团队配备情况 | 0~7 |
| 系统调试及验收方案 | 0~5 |
| 培训方案 | 0~3 |

科目字段：

| 字段 | 含义 |
|------|------|
| subject_id | 科目ID |
| subject_name | 科目名称 |
| score_range | 科目总分值区间 |
| score_units | 科目下的评分单元 |
| raw_text | 科目原文 |

### 2. 评分单元 score_unit

评分单元是实际产生一个 `0~N` 分值区间的评分对象。

有些科目下每个小项都是一个评分单元，例如“需求理解”下四个小项各 `0~3`。

有些科目整体就是一个评分单元，例如“培训方案”整体 `0~3`，其中培训计划、培训期限、培训人员、培训内容只是评分细则或检查点。

评分单元字段：

| 字段 | 含义 |
|------|------|
| unit_id | 评分单元ID |
| unit_name | 评分单元名称 |
| score_range | 评分单元分值区间 |
| score_details | 评分单元下的评分细则 |
| raw_text | 评分单元原文 |

### 3. 评分细则 score_detail

评分细则是技术标提取中最重要的细粒度对象。

每条评分细则需要拆出：

```text
评分细则 = 评价对象 + 评价特性 + 评价方法
```

例如：

```text
系统架构设计明确、合理
```

可拆成：

| 组成 | 内容 |
|------|------|
| 评价对象 | 系统架构设计 |
| 评价特性 | 明确、合理 |
| 评价方法 | 根据明确性、合理性落入不同得分档位 |

评分细则字段：

| 字段 | 含义 |
|------|------|
| detail_id | 评分细则ID |
| detail_name | 评分细则名称 |
| score_type | 主观评分或客观评分 |
| scoring_object | 评分对象，例如架构、方案、合同、证书、人员 |
| scoring_feature | 评分特性，例如明确、合理、完整、符合要求 |
| evaluation_method | 评价方法 |
| raw_text | 评分细则原文 |

## 四、评分细则的主观/客观分类

每个评分细则都要标注 `score_type`。

| score_type | 含义 | 打分方式 |
|------------|------|----------|
| subjective | 主观评分 | 根据投标文件内容质量、完整性、合理性、针对性等判断 |
| objective | 客观评分 | 根据证书、合同、数量、时间、公式等明确条件判断 |

### 1. 主观评分细则

主观评分细则通常评价方案文本。

例如：

| 评分细则 | 评价对象 | 评价特性 |
|----------|----------|----------|
| 技术方案详细、全面 | 技术方案 | 详细、全面 |
| 系统架构合理 | 系统架构 | 合理 |
| 实施计划科学合理 | 实施计划 | 科学、合理 |
| 培训方案完整详尽 | 培训方案 | 完整、详尽 |
| 验收流程清晰合理 | 验收流程 | 清晰、合理 |

主观评分的评价方法一般是档位判断：

```json
{
  "method_type": "level_judgement",
  "levels": [
    {
      "score_range": { "min": 5, "max": 5 },
      "condition_text": "方案完整详尽，管理标准和要求明确、流程清晰合理、实施措施全面到位"
    },
    {
      "score_range": { "min": 3, "max": 4 },
      "condition_text": "服务内容、标准和要求基本完整、流程合理、实施措施基本齐全"
    },
    {
      "score_range": { "min": 1, "max": 2 },
      "condition_text": "服务内容、标准、流程、实施措施等不全面，存在明显缺漏"
    },
    {
      "score_range": { "min": 0, "max": 0 },
      "condition_text": "未提交任何方案，或方案完全不匹配项目实际情况"
    }
  ]
}
```

### 2. 客观评分细则

客观评分细则通常评价证明材料。

例如：

| 评分细则 | 评价对象 | 评价特性 |
|----------|----------|----------|
| 团队人数不少于20人 | 团队人数 | 不少于20人 |
| 项目负责人具备信息系统项目管理师证书 | 项目负责人证书 | 具备指定证书 |
| 类似项目合同服务期限包含2023年1月1日以后 | 类似项目合同 | 时间满足要求 |
| 每份类似项目合同得1分 | 合同数量 | 每份计分、封顶 |

客观评分的评价方法一般是规则核验或计数：

```json
{
  "method_type": "evidence_count",
  "evidence_type": "contract",
  "unit_score": 1,
  "max_score": 8,
  "conditions": [
    "服务期限包含2023年1月1日以后",
    "提供合同扫描件",
    "合同主要内容包括项目名称、盖章页、签订日期"
  ],
  "calculation_rule": "每份符合条件的合同得1分，满分8分"
}
```

## 五、提取规则

### 1. 先提取科目

从综合评分法表中提取技术标相关大项作为科目。

报价得分属于价格分，不纳入技术标提取。

类似项目经验、团队证书等如果出现在技术标评分体系中，应保留，但标记为客观评分。

### 2. 再提取评分单元

判断一个科目下面有几个真正独立给分的单元。

判断依据：

| 原文特征 | 拆分方式 |
|----------|----------|
| “各X分”“每项X分” | 每个小项拆成一个评分单元 |
| 只给出一个总分区间 | 整体作为一个评分单元 |
| “每份X分，满分N分” | 作为一个计数型评分单元 |
| “每个证书X分” | 作为一个证据型评分单元 |

### 3. 再提取评分细则

评分细则从评分单元的原文中抽取，重点抽取：

| 信息 | 说明 |
|------|------|
| 评价对象 | 被评价的对象，如架构、方案、合同、证书、人员 |
| 评价特性 | 对对象的要求，如合理、明确、完整、符合要求 |
| 评价方法 | 满分、部分分、零分分别如何判断 |
| 主观/客观 | 标注该细则属于主观评分还是客观评分 |

### 4. 保留原文

所有科目、评分单元、评分细则都必须保留 `raw_text`。

当前阶段只提取采购文件中显式存在的信息，不人为解释主观词，也不替模型规定投标文本应该如何组织。

## 六、示例

### 示例一：主观评分

原文：

```text
系统调试及验收方案 0~5
满足在现有环境中系统调试、测试、开通等实际要求，提供的方案完整详尽，
管理标准和要求明确、流程清晰合理、实施措施全面到位，能达到相关法律法规政策要求的，得5分；
所提供方案的服务内容、标准和要求基本完整、流程合理、实施措施基本齐全的，得3-4分；
所提供方案的服务内容、标准、流程、实施措施等不全面，存在明显缺漏的，得1-2分；
未提交任何方案，或提交方案完全不匹配项目实际情况且不具备可操作性的，不得分。
```

结构化结果：

```json

  "score_range": { "min": 0, "max": 5 },
  "score_units": [

      "score_range": { "min": 0, "max": 5 },
      "score_details": [
        {
          "detail_name": "系统调试及验收方案质量",
          "score_type": "subjective",
          "scoring_object": "系统调试及验收方案",
          "scoring_feature": "完整详尽、要求明确、流程清晰合理、措施全面到位",
          "evaluation_method": {
            "method_type": "level_judgement",
            "levels": [
              {
                "score_range": { "min": 5, "max": 5 },
                "condition_text": "方案完整详尽，管理标准和要求明确、流程清晰合理、实施措施全面到位"

              {
                "score_range": { "min": 3, "max": 4 },
```
